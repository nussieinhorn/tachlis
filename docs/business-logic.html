Tachlis: Business Logic Spec

The real rules behind the Supabase migration — written down before any schema, auth, or RLS work starts, so they can be reviewed and corrected first. Several things that were simple placeholders in the prototype (a global admin toggle, a "submitted for review" message that saved nothing, an action plan that existed only because mock data said so) needed real, decided logic. This is that logic.

Auth & accounts

  • Real Supabase Auth. Email + password only for v1 — no magic link, no OAuth.
  • Email confirmation required before an account can create, edit, or comment.
  • Creating an issue always requires a confirmed account. No anonymous issue creation, no exceptions.
  • Whether supporting, voting, or commenting need an account is a per-issue owner choice — see Visibility & security below, not a global rule.

Ownership & permissions

Replaces the prototype's global "admin mode" toggle entirely — that switch, and the site-wide view-as-admin/user it powered, are being removed.

Owner + granted editors New model

  • Every issue and community has an owner — the account that created it.
  • Owners can grant other real accounts persistent, revocable edit access. This is the real backing for the Team step's "Can update this issue" checkbox — instead of being collected and thrown away, it becomes a row in an issue_editors-style table the owner can see and revoke later.
  • Communities use the identical model — owner + optional granted editors. One consistent shape for both resource types.

Super admin

The site owner's own email is the super admin — full edit access to every issue and community, site-wide, no per-resource grant needed.

View as Admin / View as User New

A per-issue toggle in the ⋮ menu. Anyone with edit rights on that issue can preview its public-facing view, with a banner marking preview mode. Direct replacement for the old global toggle — but scoped to one issue, and only usable by someone who actually has rights to it.

Issue visibility & security settings

Mostly already modeled in the wizard's Settings step. This confirms what carries forward and adds one new toggle.

Public / Private Carries forward

  • Private issues: visitor must be logged in → submits a request → owner/admin approves before they can view it.
  • Private communities stay fully hidden from non-owners/non-admins — absent from directories, search, and issue-page links, not just gated behind a screen.

Support / Vote / Comment login requirements

  • Carries forward "Support requires login" and "Vote requires login" — already exist, confirmed as real server-enforced settings.
  • New "Comments require login" — new toggle alongside the existing "Allow comments" on/off. Same shape as support/vote: one switch turns commenting on at all, the other decides if anonymous visitors can post.
Rendering shift: private data must actually be withheld via Row Level Security, so issue/community pages move from build-time static generation to per-request rendering, checked against whoever's asking.

Solution review queue

Today, a non-admin's "suggest a solution" shows a fake confirmation and saves nothing. This becomes real.

  • Suggestions go into a real pending queue, invisible to the public until reviewed.
  • The queue lives inside the issue's own Solutions section — not the general Requests inbox, since a suggestion is a different kind of thing from an access/join request. Shows a count of what's new since the admin last checked.
  • Review is a one-step decision:
    • Accept → goes live immediately, publicly visible, status "Considering." No separate staging area — accepting is publishing.
    • Reject → discarded.
  • Carries forward AI-assisted pros/cons generation ("Regenerate" once populated) plus manual pros/cons entry, unchanged.

Action Plan / Action Team triggers

Today these sections exist only because mock data happens to include an action plan. Real trigger, below.

The first-Chosen moment

1
A solution is marked Chosen for the first time ever on this issue.A one-time pop-up appears.
2
Admin picks the issue's new status. Required step in the same pop-up.
3
Admin optionally starts the Action Plan task list right there, or skips and adds tasks later via the normal inline editing.

This is a one-time moment per issue — it does not re-fire if the chosen solution changes later. Once triggered (or skipped), Action Plan and Action Team become active and public.

Requests inbox

Covers private-issue access requests and action-team join requests — the "someone is asking, an admin approves or rejects" flows.

  • Surfaced in a new header notification dropdown, under a "Requests" tab.
  • Only visible to users who own or have edit access to at least one issue/community — plain supporters never see it.
  • Approve individually, or "approve all" per issue — bulk approval doesn't span multiple issues in one click.

Notifications

The dropdown's other tab — visible to every logged-in user, not just admins.

Triggers

  • Admin/owner posts an update
  • A solution is marked Chosen
  • The issue's status changes
  • A new solution is suggested, by anyone

Notifies everyone currently supporting that issue. Each entry shows the event type and which issue it's about, with a title preview — one person may support many issues.

Migration & cleanup principles

  • Every // TODO(supabase) marker in the codebase is a real write that must land in the database — issues, communities, edits, comments, solutions, everything. Nothing stays session-local after migration.
  • Status-change side effects must be explicit, documented rules — not implicit behavior that only happens to work because of what the mock data contains.
