# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MOTIVE (formerly Tachlis; the repo, Vercel project and tachlis.org domain still use the old name) — a community problem-solving platform (public issues → proposed solutions → voting → public action tracking, "from discussion to actually solved"). Full product spec lives in `spec.md`; the real business rules (auth, ownership/permissions, visibility settings, the solution review queue, Action Plan triggers, notifications) live in `docs/business-logic.md` — read that before touching auth, permissions, or any admin-approval flow. **`docs/business-logic.md` is stale in places** (e.g. it still describes Action Plan/Team visibility as automatic — it isn't, see below) — where this file and that one disagree, this file and the code win.

**The Supabase migration is complete.** Every page and component reads and writes through `src/lib/supabase/`; there is no more mock/session-local data. `src/lib/mock-data.ts` and `src/lib/communities-data.ts` still exist, but only as shared TypeScript types (`Issue`, `Solution`, `Community`, etc.) plus small pieces of genuinely static, non-DB reference data (the `LOCATIONS` filter list, community tone → Tailwind class map). `CATEGORIES` in `mock-data.ts` is now only a **fallback/seed** — the real, live category list is DB-driven (see Categories below). If you're looking for the actual data, it's in Postgres.

## Commands

```bash
npm run dev              # start dev server (localhost:3000)
npm run build             # production build — also type-checks AND catches prerender issues `tsc` won't (see Deployment gotchas)
npx tsc --noEmit           # type-check only, no build
```

No test suite or lint script is configured. There is no Supabase CLI installed locally — schema changes go through the Supabase MCP connector (`apply_migration`, `execute_sql`, `get_advisors` against project id `edoczobzfepqpyffifhd`), not `supabase db push` or migration files on disk. Edge functions deploy the same way, via the MCP connector's `deploy_edge_function` (there is no `supabase/functions` directory on disk — function source only lives in the deployed project).

**Deploys:** Vercel project **`tachlis`** under the **Intent UX** Vercel team (`team_FZt7j8rV4mWHJCW0tJGfH20G`) — not to be confused with other unrelated projects in that same team (e.g. `worko`). It auto-deploys on every push to `main` via the GitHub integration; never deploy manually. `useSearchParams()` anywhere in the App Router **must** be wrapped in a `<Suspense>` boundary or the production build fails at the prerender step with "should be wrapped in a suspense boundary" — `tsc --noEmit` and `npm run dev` won't catch this, only `npm run build` will, so run a full build before pushing anything that touches search params (see `src/app/invite/accept/page.tsx` for the pattern: inner client component doing the `useSearchParams()` work, default export just wraps it in `<Suspense>`).

## Architecture

**Stack:** Next.js App Router + TypeScript, Tailwind v4, hand-written shadcn/ui-style components (not CLI-installed — this network has blocked the shadcn CLI's transitive deps before), Tabler icons via a shared `<Icon>` wrapper that enforces consistent stroke width, Supabase (Postgres + Auth + Edge Functions) for the backend, Resend for transactional email, `@dnd-kit/*` for drag-to-reorder.

**Rendering:** static pages use plain Server Components. `issues/[id]` and `communities/[id]` are per-request (no `generateStaticParams`) — private data is checked against the actual requester via RLS, which static generation can't do. Don't add `generateStaticParams` back to either route.

**Server → Client prop boundary gotcha:** a Server Component can't pass a React component/function reference (e.g. a Tabler icon component) as a prop into a Client Component — it fails at runtime with "Functions cannot be passed directly to Client Components." This bit the category system: `getCategories()` (server) returns a serializable `CategoryOption[]` (`{slug, label, iconSlug}`, no component reference), and the icon is resolved client-side from `iconSlug` via `getCategoryIcon()` (`src/lib/category-icons.ts`) inside the Client Component that renders it. Keep this pattern for anything else that crosses that boundary carrying an icon/component.

**Data layer (`src/lib/supabase/`):**
- `client.ts` — browser Supabase client (`createBrowserClient`), for client components. Writes (inserts/updates/deletes) happen here, directly from the component that triggers them, followed by `router.refresh()` to re-pull server data — there's no Server Actions layer.
- `server.ts` — server Supabase client (`createServerClient`, reads cookies via `next/headers`), for Server Components/Route Handlers. Queries through this client run as the requesting user's session, so Postgres RLS does the actual visibility filtering — there's no app-level "is this private" branching to get wrong.
- `queries.ts` — the read layer. Server-only (imports `server.ts`). Fetches DB rows and reshapes them into the same nested shapes (`Issue` with `.solutions[]`, `.actionPlan[]`, etc.) the UI already expects, using Supabase's embedded-select joins. Note: PostgREST embedded filters (`.eq("solutions.review_status", ...)`) only work one level deep — grandchild embeds (e.g. `action_plans.action_tasks`) can't be filtered this way and are filtered in JS after fetching instead. Solutions are also **re-sorted client-side by `sort_order`** after fetch (`getIssue()`) rather than via a PostgREST embedded `.order()`, and `chosenSolutionIds` is derived from `status === "chosen"` on the already-sorted array, not by index-matching against the raw fetch order — don't reintroduce an index-based lookup there, it silently breaks once solutions are reordered.
- `types.ts` — generated via the Supabase MCP `generate_typescript_types` tool. Regenerate after any schema change rather than hand-editing.
- `src/middleware.ts` refreshes the auth session cookie on every request — required for the server client to see a valid session.
- `src/lib/format.ts` — shared `formatRelativeTime` (short "2h ago" style, used everywhere including comments/notifications), `abbreviateLocation` ("Lakewood, New Jersey" → "Lakewood, NJ"), `abbreviateName` (first name + last initial), `isValidEmail`. Reuse these rather than writing another relative-time/email-regex helper.
- `src/lib/category-icons.ts` — fixed set of ~25 Tabler icons (`CATEGORY_ICON_OPTIONS`) an admin can pick from when adding a category on the fly, plus `getCategoryIcon(iconSlug)` with a sane fallback.

**Auth & permissions:**
- `src/lib/auth.tsx` — real `useAuth()` hook (Supabase Auth: `sendCode`/`verifyCode`/`signOut`, `onAuthStateChange`, plus `updateProfile`/`updateEmail`/`deleteAccount`). Passwordless: email → 6-digit one-time code (`signInWithOtp` + `verifyOtp`, account auto-created on first use; there are no passwords or reset flow). Needs `{{ .Token }}` in the Supabase "Magic Link" and "Confirm signup" email templates (dashboard-only setting). The confirmation link hits `src/app/auth/confirm/route.ts`, which does the `verifyOtp` exchange. `profile` includes `themePreference`, `notifyTypes`, `emailNotifyTypes` (see Notifications & theme below) — regenerate this shape if you add more `profiles` columns, it's hand-mapped, not a raw table select.
- Permission model is **owner + granted editor + one hardcoded super admin**, not a role flag: `is_super_admin()` and `has_issue_edit_access()`/`has_community_edit_access()` Postgres functions (used both inside RLS policies and callable directly as RPCs via `getIssueEditAccess()`/`getCommunityEditAccess()` in `queries.ts`) are the source of truth. Each page computes `canEdit` once server-side and threads it down as a prop — there is no global admin toggle anywhere in the app.
- Every resource (`issues`, `communities`) has an `owner_id` plus an `*_editors` grant table for delegated edit access.
- Private issues: `getIssue(id)` returns `undefined` if RLS blocks the row (not public, no approved access). The page then calls `getIssueStub(id)` — a `SECURITY DEFINER` RPC that returns just `{id, display_code, visibility}` bypassing RLS — to render the "request access" screen (`PrivateIssueGate`) instead of a bare 404. **`get_issue_stub()` deliberately does not return `title` or `owner_name`** (it used to; that leaked identifying info about a resource the requester isn't approved to see, per explicit feedback) — `PrivateIssueGate` shows a fully generic "This is private" message. Don't add title/owner back to that RPC.

**Database shape:** see `docs/business-logic.md` for the why (note some staleness caveats above); the tables (all RLS-enabled) are `profiles`, `categories`, `communities`/`community_editors`, `issues`/`issue_editors`, `issue_supports`, `issue_links`, `issue_updates`, `solutions`/`solution_votes`, `comments` (one unified table for both issue- and solution-level threads, disambiguated by nullable `issue_id`/`solution_id` with a check constraint), `action_plans`/`action_tasks`/`action_team_members`/`action_team_requests`, `private_access_requests`, `community_access_requests`, `pending_invites`, `issue_alert_subscriptions`, `notifications`, `issue_status_config`/`solution_status_config`. Notifications fan out via the `notify_issue_followers()` Postgres function (called from triggers on the originating event — e.g. inserting an `issue_updates` row), not application code — don't try to also fan them out from the client. That function now also does two more things per recipient (see Notifications below): gates the in-app insert on `profiles.notify_types`, and fires an async `pg_net` HTTP call to the transactional-email Edge Function for any type in `profiles.email_notify_types`.

**Private data — where contact details live (launch hardening, Nov 2026):** the public can read `profiles` only for `id, name, created_at` (column grants). Email, phone and notification preferences are never selectable directly: the signed-in person reads their own row with `rpc("get_my_profile")`, and organizers read other people's email/phone with `rpc("profile_contacts", { p_ids })`, which only returns people tied to something the caller manages (requesters, editors, solution submitters). Never add `email`/`phone` to a `profiles(...)` embed or `select`; it will fail with a permission error by design. Volunteers' contact details from "willing to help" live in `issue_support_contacts` (readable only by the issue's editors); action-team members' email/phone are only returned by `rpc("action_team_contacts")`. `issue_supports` and `solutions` carry no contact columns any more.

**Permissions model changes:** only the **owner** (or super admin) can delete an issue/community or transfer ownership (DB trigger `guard_owner_change`, delete policies); editors can change everything else. `pending_invites` can't be rewritten after creation (trigger). Guests can't undo supports/votes (no anonymous deletes), and nobody can insert a support/vote as another user. Issue settings are enforced in the database as well as the UI: `allow_suggest_solutions` (solution insert policy), `vote_requires_login` / `support_requires_login`, `voting_close_date` (vote insert policy). `go_live_date` / `hidden_date` are saved but deliberately not exposed in the wizard (not implemented). The UI reads these rules through `IssueSettingsProvider` (`src/components/issue/issue-settings-context.tsx`). Private communities are visible to owner, editors and approved viewers; non-members get the request-access gate (`get_community_stub`, `PrivateIssueGate kind="community"`). Timeline updates can be edited/deleted by editors. Deleting an account deletes its issues and communities (cascade), anonymises its comments ("Deleted user") and keeps its solutions on other people's issues without a name.

**Email (`send-transactional-email` v8):** the function never accepts recipients, subjects or links from the caller. It is told *which database record* to mail about (`notificationId`, invite `token`, or `kind`+`resourceId`), builds the message from the database, escapes HTML, and marks the record as mailed (`emailed_at` / `*_emailed_at`) so it can't be replayed. Links use the `SITE_URL` secret (default https://tachlis.vercel.app). It still no-ops until `RESEND_API_KEY` (and `RESEND_FROM`) are set. The invite panel also has a "Copy invite link" button so invites work without email.

**No uploads, by product decision:** users cannot store files anywhere — no community logos, no images or attachments in comments, updates or solutions; everything is text. `communities.logo_url` and all storage policies were removed and the old `community-logos` bucket is locked (private, 1-byte limit). Communities are identified by a colour + icon (`CommunityAvatar`). Don't add file inputs, `<img>` of user content, or storage buckets without an explicit product decision.

**Homepage and dashboard:** `/` is the same public showcase for everyone (no switcher); signed-in people reach `/dashboard` from the account menu (it shows a sign-in prompt when signed out and is `noindex`). The dashboard's "My issues" is capped at 4.

**Undo support/vote:** `issue_supports` and `solution_votes` both have a `delete` RLS policy (`user_id = auth.uid()` for signed-in rows, or `user_id is null` for guest rows — guest rows are only deletable by knowing their unguessable UUID, which is an acceptable tradeoff for a low-stakes "support" count). `join-panel.tsx` and `solution-card.tsx` hydrate the existing row's id on mount so a returning user's "Support"/vote button correctly shows as already-active and can be undone (opens a confirm dialog rather than silently no-op'ing, which is what clicking an already-active button used to do).

**The "first solution chosen" flow — read this before touching solution status:** the first time ever a solution on an issue is marked "Chosen," a one-time popup (`ChosenSolutionDialog`) requires picking the issue's new status, optionally seeding the Action Plan's task list, and optionally publishing the Action Plan to supporters immediately (`action_plan_visible`). On confirm it sets `issues.first_chosen_prompted_at` and **unconditionally creates the `action_plans` row** (even with zero seeded tasks — this is required, `ActionPlanPanel` needs a real `action_plans.id` to attach tasks to later; it used to only create the row `if (tasks.length > 0)`, which left admins with no way to ever open a working Action Plan panel on issues where they didn't seed tasks up front — that bug is fixed but watch for it recurring). **There are currently two places that can mark a solution "chosen"** — the card's own status-badge dropdown (`solution-card.tsx`, `changeStatus()`) and the admin edit sheet (`solution-edit-dialog.tsx`, opened via the pencil icon). **Both must check `isFirstChosen` and defer to `ChosenSolutionDialog` instead of writing `status: "chosen"` directly** — a plain status write silently skips `first_chosen_prompted_at`/`action_plans` creation entirely, which is a real regression that shipped once already. If you add a third way to change a solution's status, it needs this same guard.

**Action Plan / Action Team — always-on-for-editors architecture:** `issues.action_plan_visible` (default `false`) gates visibility for non-editors only. Once `first_chosen_prompted_at` is set **and** the `action_plans` row exists, `canEdit` users always see the full `ActionPlanPanel` (task list + nested Action Team), regardless of `action_plan_visible` — they can prep tasks privately before publishing. The publish toggle (`ActionPlanVisibilityToggle`) is rendered **inside** `ActionPlanPanel` as a banner strip at the top of the card (not a separate card/component above it) — non-editors only ever see the whole panel once that toggle is on. `ActionTeamPanel` is rendered **nested inside** `ActionPlanPanel`, directly below the task list, not as a sibling section on the issue page — it inherits the exact same gating as a result, which is the intended behavior ("Action Team always shows together beneath the Action Plan, with the same permissions").

**Categories — DB-driven with a static fallback:** `categories` (slug, label, `icon_slug`) is the live source of truth, seeded from the old static 25-entry list but now writable — **any authenticated user can insert a new category** (RLS: `for insert to authenticated with check (true)`; update/delete stay `is_super_admin()`-only). `getCategories()` in `queries.ts` is the server read; `create-issue-dialog.tsx`'s category picker also fetches it client-side (for the live "Add category…" flow) and posts new rows with an icon chosen from the fixed `CATEGORY_ICON_OPTIONS` grid. `CATEGORIES` in `mock-data.ts` is kept only as a synchronous fallback for a couple of call sites that haven't been threaded a live list (`issue-card.tsx`, `my-issue-row.tsx`, `issues/[id]/page.tsx`'s `getCategory()`) — a category added on the fly will render correctly everywhere that *is* threaded a live list (the homepage/`issue-browser.tsx` path) but may show a generic fallback icon on those few not-yet-wired call sites until they're updated to accept a `categories` prop too, same pattern as `issue-browser.tsx`.

**Notifications & theme (`/profile` → Preferences tab):** `profiles.theme_preference` (`system`/`light`/`dark`, drives `src/lib/theme.tsx`'s `ThemeProvider` + `.dark` class on `<html>`, persisted to the DB when signed in and to `localStorage` as a pre-hydration/guest fallback — see the inline script in `layout.tsx` that avoids a flash of the wrong theme), `profiles.notify_types` (text[], which event types create an in-app `notifications` row — checked inside `notify_issue_followers()`), `profiles.email_notify_types` (text[], subset of the above that should *also* email — checked in the same function, which then calls the `send-transactional-email` Edge Function via `pg_net`). **This lives on `/profile`, not `/settings`** — `/settings` is gated to `is_super_admin()` only, so anything a regular user needs to control must not go there (this was a real bug: the theme toggle was originally built on `/settings` and was completely unreachable by non-admins).

**Transactional email (`send-transactional-email` Edge Function, Resend):** handles four types — `invite` (pending_invites), `access_approved`, `access_requested` (looks up the resource's owner+editors via service-role key rather than being passed a `to`), and `issue_notification` (fired from `notify_issue_followers()` for `email_notify_types`). **It no-ops gracefully (`{sent: false, reason: "RESEND_API_KEY not configured"}`) until `RESEND_API_KEY` (and optionally `RESEND_FROM`) is set as a secret on the Supabase project** — nothing currently breaks without it, emails just silently don't send. Don't assume email is actually being delivered in this environment without checking that secret is set.

**Invites (`pending_invites` + `/invite/accept`):** admins invite by email (comma-separated, Viewer/Editor role) from `share-access-panel.tsx`, the issue wizard's Team step, or the community wizard's Invite step — all three write a `pending_invites` row and call the email Edge Function, replacing the old behavior of silently no-op'ing when the email didn't match an existing account. `accept_pending_invite(p_token)` is a `SECURITY DEFINER` RPC that grants access (inserts into `issue_editors`/`community_editors` for `editor`, or approves a `private_access_requests`/`community_access_requests` row for `viewer`) and returns `{resource_type, display_code}` so `/invite/accept` can redirect there. Visiting a resource directly without an invite still goes through the existing self-serve pending-request flow (`private_access_requests`/`community_access_requests`, status `pending`→`approved`/`rejected`/`revoked`).

**Header inbox (`src/components/inbox-dropdown.tsx`):** a bell icon next to the account menu, visible when signed in. Two tabs: Notifications (every signed-in user, reads `notifications` including its `payload` jsonb for specific copy like the new status label or chosen-solution title, not just the generic event-type label) and Requests (shown if the user owns or edits at least one issue/community, or is the super admin — aggregates pending `private_access_requests`, `community_access_requests`, and `action_team_requests`, each showing a Viewer/Editor role picker + check/✕ approve-reject buttons for the two access-request kinds — `action_team` requests don't have a role concept so keep plain Approve/Reject there).

**Short display IDs:** `issues.display_code` / `solutions.display_code` / `communities.display_code` are unique 4-digit zero-padded text columns (Postgres column defaults pull from a per-table sequence) used in URLs and UI display. The real `id` (uuid) stays the actual primary/foreign key everywhere internally.

**Access model — edit vs. view-and-support:** no separate "role" column. "Edit" tier = a row in `issue_editors`/`community_editors` (gates `canEdit`). "View-and-support" tier = an `'approved'` row in `private_access_requests` / `community_access_requests` with **no** matching editors row. `status` on both request tables is plain text (`'pending' | 'approved' | 'rejected' | 'revoked'`) — a requester can re-request after rejection/revocation via a dedicated RLS policy that only allows flipping their own row from `rejected`/`revoked` back to `pending`.

**Share/access panel (`src/components/share-access-panel.tsx`):** the single "Share" button on both issue and community pages, branching on `visibility`/`privacy`. Public → the existing link-share dialog (`issue/share-panel.tsx`). Private → real tabs (Pending / Active / Revoked, `src/components/ui/tabs.tsx`) rather than stacked sections: Pending splits "Invites sent" (from `pending_invites`, revocable) from "Access requests" (self-serve, role-picker + check/✕); Active lists owner/editors/approved viewers with per-row Revoke; Revoked lists rejected/revoked requests.

**Solutions:** `manage-solutions-dialog.tsx` has Pending/All-solutions tabs (not stacked); the All tab supports drag-to-reorder via `@dnd-kit/*`, writing `solutions.sort_order`. Per-solution admin edit (title/description/status-dropdown/pros/cons) is one dialog, `solution-edit-dialog.tsx`, opened either from the card's `⋮` menu or a pencil icon in the detail `Sheet` header — don't build a second edit surface, extend this one. Solution-level comments (`CommentThread` inside the card's `Sheet`) must be passed the issue's `commentsEnabled`/`commentsRequireLogin` explicitly — they don't inherit it automatically, and it's an easy prop to forget when adding a new solution-rendering call site (currently threaded through `issue-solutions-section.tsx` and `other-proposals.tsx`).

**Wizards (`create-issue-dialog.tsx`, `create-community-dialog.tsx`):** both open on a **Privacy step first** (lock/globe explanation cards with a Continue button per option) before any other step, pre-selecting `visibility`/`privacy` for the later Settings step (where it's still changeable). Both share `LocationSearch` (`src/components/location-search.tsx` — Nominatim `addressdetails=1`, abbreviated "City, ST" output, debounced with a loading state) for their location field. The issue wizard's Settings step (and the merged edit dialog, see below) groups toggles under headings (Visibility / Comments & permissions / Timeline / Community) with location+category in a 50/50 grid, rather than one flat toggle grid.

**Issue settings — one dialog, not two:** `IssueSettingsDialog` was deleted; `CreateIssueDialog` in edit mode (`editIssue` prop) is now the only surface for editing an existing issue's settings, opened from both the issue-detail "Edit" button and (previously) the three-dot menu's "Issue settings" item — the redundant menu item was removed since it opened an identical, separately-maintained form. If you need to add an issue setting, add it once, here.

**Mobile sticky support bar (`src/components/issue/mobile-support-bar.tsx`):** `md:hidden`, becomes visible via an `IntersectionObserver` on a `#support-sentinel` div placed right after the description block on the issue page. It's a second, independent "quick support" surface (one-tap level-1 support + the existing `ShareAccessPanel`) — not wired to the main `JoinPanel` instance's local state, so it calls `router.refresh()` after supporting to keep both in sync rather than sharing state directly.

**Status labels/colors — DB-backed but not read yet:** `issue_status_config`/`solution_status_config` (key/label/color_token) are editable from `/settings` (admin-only) and persist correctly, but **`status-badge.tsx` and `solution-card.tsx`'s `SOLUTION_STATUS_CONFIG` still read the old hardcoded label/color constants** — the config tables aren't wired into the actual badge rendering yet. Don't assume editing a status color in Settings changes anything visible until that read-side wiring is done; this is a known, deliberately-scoped-out gap, not a bug to silently "fix" by guessing at intent — ask before doing that wiring, since it touches several render paths.

**Component conventions:**
- `src/components/ui/` — hand-written shadcn-style primitives (not generated by the shadcn CLI).
- `src/components/issue/` — everything scoped to a single issue's detail page (solution cards/drawer, action plan, action team, comments, admin dialogs). Most of the issue detail page's complexity lives here, not in `src/app/issues/[id]/page.tsx` itself.
- Dialogs in this codebase don't use Radix's `DialogTrigger`; they take a `trigger: ReactNode` prop (optional on dialogs that also support a fully controlled `open`/`onOpenChange` pair, e.g. `solution-edit-dialog.tsx`), wrap it in `<span onClick={() => setOpen(true)}>`, and manage `open` state internally alongside a `reset(open)` function that clears form state on close. Follow this pattern for new dialogs rather than the shadcn default.
- Every "admin-only" or "owner-only" UI branch takes a `canEdit: boolean` prop computed by the nearest Server Component ancestor — don't reach for a context/hook for this, thread the prop.
- Dark mode: components should stick to the semantic Tailwind classes already in use (`bg-background`, `text-foreground`, `border-border`, etc., all CSS custom properties) — those automatically pick up the `.dark` palette in `globals.css` with zero extra work. Only reach for an explicit `dark:` variant if you're using a hardcoded/one-off color that isn't one of the semantic tokens.
